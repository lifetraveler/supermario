# 队列调度（Queue Task）设计说明

## 1. 背景

项目里需要"并发跑一批任务，边跑边补，直到跑够为止"的模式。典型场景：

- 派部队去打巨兽、采集、做活动
- 日常开免费宝箱、领取任务奖励
- 后续可能还有更多类型

这些场景的**执行形态**相同（都是队列 + 自动补任务），**业务内容**不同。

如果为每一种业务都复制一份完整的调度代码，会产生：

- 大量重复（tick 循环、paused / exit 处理、info 刷新……）
- 加一种业务就要改一堆地方
- GUI 配置每加一种都要手写一遍

因此引入统一的分层设计。

---

## 2. 术语约定（非常重要）

本项目把"队列"和"业务"严格区分：

| 术语 | 归属 | 含义 | 出现在哪 |
|---|---|---|---|
| **Queue（队列）** | 开发 | 数据结构 / 调度模式 | `scheduler/`、`tasks/queue/`、内部变量 |
| **Task** | 开发 | 单个可执行单元 | 全项目通用 |
| **Troop（部队）** | 游戏 | **战斗 / 派出类**业务的术语 | 仅 HuntMonsterTask 等战斗类 |
| **Daily（日常）** | 游戏 | 日常类业务 | ClaimStaminaTask 等日常类 |
| **Activity（活动）** | 游戏 | 活动类业务 | CesareFightTask 等 |

**三条铁律**：

1. 类名里出现 **Queue** → 属于开发层，禁止 import 任何业务包
2. 类名里出现 **业务词**（Troop / Daily / Activity / …）→ 属于业务层
3. **UI / log 里不出现 Queue 字样**，玩家视角只看到游戏概念

## 4. 各层职责

### 4.1 `TaskQueue` / `TaskFactory`（scheduler）

纯数据结构 + 补任务逻辑。它只认识"工厂"和"任务"，完全不知道 SG 的存在。

- `TaskQueue.add_factory(f)`：注册一个工厂
- `TaskQueue.tick()`：每次调用时检查并补任务
- `TaskQueue.all_done()`：是否全部完成
- `TaskQueue.get_snapshot()`：获取进度快照

### 4.2 `QueueTaskBase`（tasks/queue）

把 TaskQueue 塞进 SGBaseTask 的生命周期里。**唯一职责**：让"跑一个队列"这件事变成"跑一个普通任务"。

- 提供统一的 `run()`，处理 tick / paused / exit
- 提供统一的 `_update_info()`
- 定义抽象接口 `_build_factories()`，让子类告诉它跑什么

### 4.3 `UnifiedQueue`（tasks/queue）—— JSON 配置驱动


业务定义不在代码里，而在 `configs/task_config.json`：

- `task_types` 段：每种任务类型的定义（默认值、参数表）——等价于旧 `registrations/reg_*.py`
- `machines` 段：多设备 / 多应用 / 多分身的实例配置（本期只消费第一条 enabled 链）

配套代码侧设施：

- `task_type_map.TASK_TYPE_MAP`：type 短 id → 任务类（唯一留在代码里的映射）
- `config_loader/`：解析 JSON、字段覆盖链（task 覆盖 → defaults → params.default）、结构校验

webui 只需读写 `configs/task_config.json` 即可控制全部参数。

## 5. 数据流
```
用户启动任务
     │
     ▼
UnifiedQueue.__init__()
     │
     ├─ config_loader.load(configs/task_config.json)
     │     └─ 结构校验 + 字段覆盖链（task → defaults → params.default）
     │        错误在启动即抛（缺文件 / 引用未定义 type / 缺映射）
     │
     └─ _resolve_task_classes()：type → TASK_TYPE_MAP 里的任务类
     │
     ▼
QueueTaskBase.run()
     │
     ├─ 构造 TaskQueue，全局参数来自 _queue_global_params()（JSON）
     │
     ├─ 调用 _build_factories()
     │       └─ 遍历 JSON 里 enabled 的任务条目 → TaskFactory
     │
     ├─ while not all_done():
     │     queue.tick()          ← 队列按 Max Active 自动补任务
     │     _update_info()        ← 刷新 UI
     │     sleep(tick_interval)
     │
     └─ queue.stop()
```

## 6. 配置文件（configs/task_config.json）

单文件双段结构，webui 直接读写：

```
task_types[]  定义段：type / name_prefix / description /
              defaults{count,max_active,requires_march_queue,
                       next_trigger_delay,one_shot,cron} /
              params[{name,attr,default,widget,desc}]
machines[]    实例段：machine → app(package) → user(user_id) →
              {queue{tick_interval,continue_after_failure}, tasks[]}
```

实例条目覆盖链：`tasks[] 条目字段 → task_types[].defaults → params[].default`。
只写用户改过的值，webui 保存时不必携带全量默认。

widget 显式声明控件的渲染方式：`switch / number / text /
drop_down{options} / multi_drop_down{options}`，不再依赖 GUI 框架推断。

## 7. 如何新增一种业务

以"新增副本扫荡"为例：

### Step 1：写一个业务任务类

```python
# src/sg/tasks/world/DungeonSweepTask.py
class DungeonSweepTask(SGBaseTask):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.name = "Dungeon Sweep"
        self.default_config.update({"Dungeon ID": 1})
        ...

    def run(self):
        dungeon_id = int(self.config.get("Dungeon ID", 1))
        ...
```

### Step 2：在 task_config.json 加定义段

```jsonc
// configs/task_config.json → task_types[] 追加：
{
  "type": "Dungeon Sweep",
  "name_prefix": "Dungeon Sweep副本扫荡",
  "description": "副本扫荡。Sweep dungeon.",
  "defaults": {
    "count": 3, "max_active": 1, "requires_march_queue": false,
    "next_trigger_delay": 0.0, "one_shot": false, "cron": ""
  },
  "params": [
    { "name": "Dungeon ID", "attr": "dungeon_id", "default": 1,
      "widget": { "type": "number" }, "desc": "副本 ID" }
  ]
}
```


### Step 3：在 task_type_map 注册类

```python
# src/sg/tasks/task_type_map.py
TASK_TYPE_MAP = {
    ...,
    "Dungeon Sweep": DungeonSweepTask,
}
```

**完成。** 定义在 JSON、类解析在映射表，无需改任何队列代码；
是否启用、跑几次由 machines 段的 tasks[] 条目决定。


## 8. 禁止事项

| 禁止 | 原因 |
|---|---|
| 在 `queue/` 包里 import 任何业务包 | 破坏"与业务无关"的约定，形成循环依赖 |
| 在 `queue/` 包里的类名 / 注释出现"部队""巨兽""宝箱" | 这些是业务术语，应留在业务包里 |
| 在业务文件里再写一遍 tick / paused / exit 处理 | 应该在 QueueTaskBase 里统一 |
| 在业务 JSON 里写 import 路径 / 类名 | 类解析只能走 task_type_map，字符串路径写错要到运行时才爆 |
| 在 UI 文案 / log 里出现 "Queue" | 玩家视角只应看到游戏术语 |

## 9. 常见问题

**Q：为什么定义段和实例段放同一个文件？**

A：单文件是用户决策——webui 一次读写拿到全部状态。
代价是 webui 保存时会携带定义段；靠"定义段只由开发者改"的约定避免冲突。

**Q：`self._factories.clear()` 是必要的吗？**

A：是。如果同一个任务实例被 run 两次（比如测试里），
保留旧工厂会导致重复提交。clear 保证每次 run 都是干净的。

**Q：业务名词还能出现在代码里吗？**

A：能，但只允许出现在两类地方：业务任务类自身
（HuntMonsterTask 等，SGBaseTask 子类）和 JSON 的
name_prefix / description / params[].name。
队列层（scheduler / tasks/queue / config_loader）仍然零业务词。
